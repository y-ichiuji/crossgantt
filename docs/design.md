# Backlog 横断ガントチャート（CrossGantt for Backlog）設計ドキュメント

- ステータス: v1 実装済み
- 最終更新: 2026-09-10

> 設計時のドラフトを、実装で確定した内容に合わせて更新したものです。設計時に「要検証」としていた項目の結論は §13 にまとめています。

---

## 1. 背景と課題

Backlog には標準のガントチャート機能がありますが、**1 プロジェクト単位でしか表示できません**。そのため、以下のような状況で全体像を把握できません。

- 1 人のメンバーが複数プロジェクトを掛け持ちしており、そのメンバーの負荷やスケジュールの重なりが見えない
- マネージャーが担当する複数プロジェクトを横並びで比較できない
- プロジェクトをまたいだ期日の衝突・遅延が、各プロジェクトのガントを開き直さないと分からない

一方で Backlog API v2 の課題検索エンドポイント `GET /api/v2/issues` は `projectId[]` と `assigneeId[]` を**複数指定できる**ため、横断的な課題取得自体は API 側でサポートされています。本アプリはこの点に着目し、「複数プロジェクト × 複数ユーザーをまとめて 1 枚のガントチャートに描画する」ビューアを提供します。

## 2. 提供価値（このアプリで実現すること）

1. **横断表示**: 複数プロジェクト・複数担当者の課題を 1 枚のタイムラインに描画する
2. **担当者軸での可視化**: 「プロジェクト別」だけでなく「担当者別」に行をグルーピングし、個人の稼働の重なりを見えるようにする
3. **遅延の即時把握**: 期限超過かつ未完了の課題を視覚的に強調する
4. **共有可能な URL**: 表示条件（対象プロジェクト・担当者・期間・グルーピング）を URL に載せ、チーム内でそのままリンク共有できる

## 3. スコープ

### やること

- Backlog の OAuth 2.0 によるログイン（単一スペース）
- プロジェクト・担当者・期間・ステータスによるフィルタ
- 担当者別 / プロジェクト別 / マイルストーン別のグルーピング表示
- 日 / 週 / 月のズーム切り替え
- 遅延課題のハイライトと、担当者ごとのサマリー（件数・遅延件数）
- 課題バーのクリックで Backlog の該当課題を新規タブで開く
- 表示条件の URL 共有
- Google Apps Script（ウェブアプリ）へのデプロイ

### やらないこと（スコープ外）

| 項目                                           | 理由                                                                           |
| ---------------------------------------------- | ------------------------------------------------------------------------------ |
| ガント上でのドラッグによる期日変更（書き込み） | 読み取り専用と決定。更新系 API を使わないことで事故と実装コストを避ける        |
| 複数 Backlog スペースの横断                    | 1 セッションにつき 1 スペース。ユーザー同一性の名寄せ問題も発生するため        |
| 課題間の依存関係（先行 / 後続）の矢印描画      | Backlog に順序依存関係の概念が存在しないため。表現できるのは親子課題の階層のみ |
| クリティカルパス算出・リソース平準化           | 上記の依存関係が取得できないため成立しない                                     |

## 4. 想定ユーザーとユースケース

| ユーザー                 | ユースケース                                                                |
| ------------------------ | --------------------------------------------------------------------------- |
| プロジェクトマネージャー | 自分が見ている複数プロジェクトを 1 画面で比較し、期日の衝突を早期に発見する |
| チームリード             | メンバーごとに行を並べ、特定メンバーに負荷が集中していないかを確認する      |
| メンバー本人             | 自分に割り当てられた全プロジェクトの課題を時系列で俯瞰し、着手順を決める    |

### 5.3 描画ルール

| ケース                              | 描画                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------------- |
| `startDate` と `dueDate` の両方あり | 期間バーとして描画                                                                                 |
| `dueDate` のみ                      | 期限日 1 日分のマーカー（◆）として描画                                                             |
| `startDate` のみ                    | 開始日から本日までのバー（末端を破線で表現）                                                       |
| どちらも無し                        | タイムラインに描画せず、「日付未設定」セクションに集約                                             |
| `dueDate < 本日` かつ未完了         | バーを警告色にし、行ヘッダに遅延バッジを表示                                                       |
| 親子課題                            | 同一プロジェクト内では親課題の下に子課題をインデント表示（グルーピングがプロジェクト別のときのみ） |
| マイルストーン                      | プロジェクト別グルーピング時に、`releaseDueDate` を縦マーカーとして重ねる                          |

- バーの色は Backlog のガントチャートと同じくステータスの色（`status.color`）を使う。
  Backlog のステータス色は明暗が混在するため、背景の相対輝度から文字色（白 / 濃色）を選ぶ
- 行ヘッダーには担当者のアイコンを並べる。プロジェクトの区別はグルーピングと
  絞り込みパネル側の色で足りるため、行ごとの色チップは置かない
- ホバー時のツールチップに、課題キー・件名・期間・ステータス・担当者・予定工数 / 実績工数を表示する
- 今日は縦線ではなく、その日の列全体を淡く塗って示す。区切りはヘッダー下段の目盛りに
  合わせ、日ズームなら 1 日分、週 / 月ズームなら今日を含む 1 週間分になる。
  土日は背景を淡いグレーにする
- 日本の祝日も稼働日ではないので、土日と同じ色で塗る。ヘッダーは不透明で帯を
  覆い隠すため、日ズームの目盛り側にも同じ色を付け、`title` に祝日の名称を出す
- 今日の帯・土日・祝日・月境界はいずれも背景レイヤー（`z-index: 0`）に置く。固定表示の
  課題名カラム（`z-index: 2`）より必ず奥になるため、横スクロールしても課題名を隠さない
- 日付の区切りが分かるよう、日ズームでは 1 日ごと、週 / 月ズームでは 1 週ごとに薄い罫線を引く。
  要素を日数分並べるとノード数が増えるため、繰り返しグラデーションで描く

## 6. 技術構成

Google Apps Script のウェブアプリとして公開します。社内に配るときに Google アカウントの
ログインをそのまま使えること、追加のインフラ契約が要らないことを重視した選択です。

| レイヤー     | 採用技術                                                                                         | 備考                                                    |
| ------------ | ------------------------------------------------------------------------------------------------ | ------------------------------------------------------- |
| ランタイム   | Google Apps Script（V8）                                                                         | `pnpm deploy` で clasp から公開する                     |
| サーバー     | 自前の同期実装（`UrlFetchApp`）                                                                  | API プロキシ。Apps Script に非同期を待つ手段が無いため  |
| 画面の配信   | `HtmlService`                                                                                    | テンプレートに JS / CSS を差し込んで 1 ページとして返す |
| クライアント | React 19 + Vite                                                                                  | バンドルは 1 ファイルにまとめて HTML へ差し込む         |
| サーバー呼出 | `google.script.run`                                                                              | 同一オリジンの API エンドポイントを持てないため         |
| ガント描画   | 自前実装（CSS Grid + 絶対配置バー）                                                              | 後述の理由によりライブラリを使わない                    |
| 状態         | 表示条件 + React state                                                                           | 共有時はウェブアプリの URL にクエリとして載せる         |
| 永続化       | `PropertiesService`（トークン）+ `localStorage`（直前のスペース）+ `IndexedDB`（直前の表示条件） | 利用者ごとに分かれた領域にトークンを置く                |

### ランタイム由来の制約

Apps Script には `fetch` も `URL` も `URLSearchParams` も `setTimeout` も無く、
Promise を待つ手段もありません。そのためサーバー側は次の方針で書いています。

- すべて同期処理。並列化は `UrlFetchApp.fetchAll` に対応する `Fetcher`
  （複数リクエストをまとめて受け取る関数）へ委ねる
- Apps Script のグローバルに触るのは `src/server/gas/` だけに閉じる。上位の
  モジュールは同期関数と単純な型しか見ないため、テストで Apps Script を模す必要がない
- 構文は esbuild で ES2019 相当まで落とす。V8 ランタイムがどの ECMAScript 版まで
  含むかは公表されていないため、広く通る範囲に寄せる
- 組み込みの不足（`Array.prototype.toSorted`）はポリフィルで補う
- `ScriptApp` には触れない。Apps Script の承認スコープはコードの静的解析で決まるため、
  参照するだけで「トリガーの管理」まで含むスコープを利用者全員に承認させることになる。
  この画面に必要なのは外部サービスへの接続だけなので、Web アプリの URL は設定で受け取る
- `UrlFetchApp` は 2KB を超える URL を受け付けない。プロジェクトやステータスの
  ID を並べるだけで届いてしまうため、課題取得はプロジェクトを URL に収まる組へ
  分けて問い合わせ、結果を課題 ID でマージする。それでも収まらない場合は
  担当者・ステータスの絞り込みを Backlog へ渡すのをやめ、取得後に同じ条件で
  絞る（`src/server/backlog/issues.ts`）
- クライアントのバンドルは Base64 にして運ぶ。`HtmlService` はファイルの中身を
  HTML として解析するため、`i<n` のような比較演算子をタグの開始と見なして内容を
  作り替えてしまう（224,247 文字が 170,468 文字まで削られ、React が起動しなかった）。
  Base64 には `<` も `&` も現れないので解析されても変化しない。同じ理由で、
  テンプレートに書くスクリプトでも比較演算子の `<` を使わない
- `pnpm smoke` が成果物を読み、禁止した機能を使っていないことを検査する

### ガントライブラリを使わない理由

- 数百行規模の描画になるため、行の仮想化と横スクロール同期を自前で制御したい
- React 19 との互換性が保証されたガントライブラリが限られる
- v1 は読み取り専用でありドラッグ編集が不要なため、必要な描画ロジックが「日付 → x 座標の線形変換」に収まる

x 座標は `left = (startDate - rangeStart) / dayMs * pxPerDay`、`width = (dueDate - startDate + 1day) / dayMs * pxPerDay` で決まります。ズーム切り替えは `pxPerDay` を変えるだけです。

## 7. Backlog API 連携設計

### 7.1 使用するエンドポイント

すべて `https://{space}/api/v2/...` に対し、`Authorization: Bearer <アクセストークン>` を付与して呼び出します。

| 用途                             | エンドポイント                                   | レート制限区分 |
| -------------------------------- | ------------------------------------------------ | -------------- |
| 自分の情報取得                   | `GET /api/v2/users/myself`                       | Read           |
| 担当者のアイコン                 | `GET /api/v2/users/{userId}/icon`                | **Icon**       |
| プロジェクト一覧                 | `GET /api/v2/projects?archived=false`            | Read           |
| プロジェクトの参加ユーザー一覧   | `GET /api/v2/projects/{projectIdOrKey}/users`    | Read           |
| プロジェクトのステータス一覧     | `GET /api/v2/projects/{projectIdOrKey}/statuses` | Read           |
| プロジェクトのマイルストーン一覧 | `GET /api/v2/projects/{projectIdOrKey}/versions` | Read           |
| 課題検索（本体）                 | `GET /api/v2/issues`                             | **Search**     |
| 課題件数                         | `GET /api/v2/issues/count`                       | **Search**     |
| レート制限状況                   | `GET /api/v2/rateLimit`                          | Read           |

### 7.2 課題検索のパラメータ設計

`GET /api/v2/issues` に対して以下を組み立てます。

| パラメータ                      | 値                                     | 意図                                     |
| ------------------------------- | -------------------------------------- | ---------------------------------------- |
| `projectId[]`                   | 選択中のプロジェクト ID 群             | 複数プロジェクト横断の要                 |
| `assigneeId[]`                  | 選択中の担当者 ID 群（未選択なら省略） | 複数ユーザー横断の要                     |
| `statusId[]`                    | 選択中のステータス ID 群               | 既定では完了以外                         |
| `dueDateSince` / `dueDateUntil` | 表示期間                               | 期間で絞る                               |
| `count`                         | `100`（API 上限）                      | 1 リクエストあたりの取得件数を最大化する |
| `offset`                        | `0, 100, 200, ...`                     | ページング                               |
| `sort`                          | `dueDate`                              | 安定した順序でページングするため         |
| `order`                         | `asc`                                  | 同上                                     |
| `keyword`                       | 任意                                   | キーワード検索                           |

#### 期間フィルタの設計（実装で確定した方式）

`startDateSince/Until` と `dueDateSince/Until` は AND 条件です。素直に `dueDateSince`／`dueDateUntil` だけを指定すると、表示期間を「またいでいる」課題（開始日が期間より前で、期限日が期間より後）を取りこぼします。

区間の重なり条件は `startDate <= 表示期間の終了日 かつ dueDate >= 表示期間の開始日` です。これはそのまま `startDateUntil` と `dueDateSince` の組み合わせで表現できます。ただしこの条件は、開始日・期限日のどちらかが未設定の課題を除外してしまいます。そこで実装では次の 3 本のクエリを投げ、課題 ID でマージして重複排除します。

| #   | 条件                                               | 拾える課題                                                                     |
| --- | -------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1   | `startDateUntil = to` かつ `dueDateSince = from`   | 開始日・期限日の両方を持ち、表示期間と重なる課題（期間をまたぐ長期課題を含む） |
| 2   | `dueDateSince = from` かつ `dueDateUntil = to`     | 期限日が表示期間内にある課題（開始日が未設定のもの）                           |
| 3   | `startDateSince = from` かつ `startDateUntil = to` | 開始日が表示期間内にある課題（期限日が未設定のもの）                           |

**仕様として許容する取りこぼし**: 「開始日のみが設定されていて、その開始日が表示期間より前」の課題はどのクエリにも掛かりません。バーとしては描ける形（`open-ended`）なので理屈のうえでは表示されうるものですが、これを拾うには期間下限のないクエリを毎回追加することになり、Search 区分のレート制限を余分に消費します。表示期間を広げれば拾えることもあり、取りこぼしを許容する判断としています。

`startDate` も `dueDate` も未設定の課題は、どの日付条件でも除外されます。これを絞り込む API パラメータは存在しないため、「日付未設定を含む」を有効にしたときだけ日付条件なしの 4 本目を投げ、取得結果から両方が空のものだけを残します。

### 7.3 ページング

`count` の上限は 100 です。実装ではまず `GET /api/v2/issues/count` で件数を取得し、必要なページ数を算出してから `offset` を並列に投げます（逐次にページを進めるより待ち時間が短くなるため）。件数が 0 のクエリではページ取得を行いません。

暴走防止のため 1 クエリあたり 25 ページ（2,500 件）を上限とし、打ち切った場合は UI に「件数が多いため一部のみ表示しています」と明示します。**黙って切り捨てないこと**を設計上の要件とします。

### 7.4 レート制限への対応

Backlog API のレート制限は Read / Update / **Search** / Icon の 4 区分に分かれており、区分ごとに 1 分あたりの上限があります。上限値はプラン（Free / 有料）によって異なるため、ハードコードせず `GET /api/v2/rateLimit` で取得します。公式ドキュメントの例では Search が 150 req/min となっています。

課題検索は Search 区分に該当し、本アプリで最も多く呼ぶエンドポイントです。以下で対応します。

- 課題取得の並列度を最大 5 に制限する（クエリ本数の並列度は 2）
- レスポンスヘッダ `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset` を記録する
- HTTP 429 を受けたら `Retry-After` または `X-RateLimit-Reset` を見て待機し、リトライする（既定 2 回まで）
- ただし待機が 8 秒を超える場合はリトライせず 429 をそのままクライアントへ返す。1 分待つとリクエストがタイムアウトして体験が悪化するため、UI で「しばらく待ってから再読込してください」と案内するほうが良いと判断した
- UI には 1 回の読み込みで消費した Backlog API リクエスト数を表示する

**負荷見積もり**: 10 プロジェクト × 平均 300 課題 = 3,000 件 → `count=100` で 30 リクエスト。Search 区分 150 req/min に対して 1 回の読み込みで 30 消費する計算になり、連続リロードには耐えられないため後述のキャッシュが重要になります。

### 7.5 ステータスの扱い

Backlog はプロジェクトごとにカスタムステータスを追加できるため、ステータス ID を `4 = 完了` のように決め打ちしてはいけません。選択中の各プロジェクトについて `GET /api/v2/projects/{id}/statuses` を呼び、以下のように扱います。

- フィルタ UI では**ステータス名**で束ねて表示する（複数プロジェクトで同名 ID 違いが存在しうるため）
- API に渡すときは、選択されたステータス名に対応する全プロジェクト分の ID を `statusId[]` に展開する
- 「完了」判定は次のヒューリスティックで行う。**Backlog API のステータスには完了フラグが存在しない**（`id` / `projectId` / `name` / `color` / `displayOrder` のみ）ため、次善の策として実装した
  - `id === 4`（スペース共通の既定ステータス。カスタムステータスには 5 以降が割り当てられる）
  - または名称が `完了` / `Closed`（前後の空白と大文字小文字は無視）
- 上記で判定できない独自の完了ステータスがある環境では、ステータスフィルタでユーザーが明示的に選択できる

### 7.6 担当者一覧の取得

選択中プロジェクトそれぞれについて `GET /api/v2/projects/{id}/users` を呼び、ユーザー ID で重複排除して統合したものを担当者フィルタの選択肢とします。スペース全体の `GET /api/v2/users` ではなくプロジェクト単位にすることで、無関係なユーザーが候補に並ぶのを防ぎます。

## 8. サーバー API 設計

### 8.1 なぜプロキシが必要か

Backlog API はブラウザからのクロスオリジンリクエストを想定しておらず、CORS ヘッダーが返らない前提で設計します（仮に許可されていたとしても、レート制限の集中管理とキャッシュのためにプロキシを経由させる方針は変えません）。

### 8.2 入口

ウェブアプリは URL を 1 本しか持てないため、入口は次の 3 つだけです。

| 入口                        | 説明                                                             |
| --------------------------- | ---------------------------------------------------------------- |
| `doGet(e)`                  | 画面の配信。`code` が付いていれば OAuth のコールバックとして扱う |
| `apiCall(name, paramsJson)` | `google.script.run` から呼ばれる API 本体                        |
| `include(name)`             | HTML テンプレートから JS / CSS を差し込むためのヘルパー          |

`apiCall` の `name` で処理を振り分けます。パラメータはクエリ文字列と同じく文字列だけで
表し、ID の一覧やフラグの解釈を `shared/filter.ts` とクライアント側で共有します。

| name        | 説明                                                                 |
| ----------- | -------------------------------------------------------------------- |
| `session`   | 現在のセッション情報。未ログインなら 401 相当                        |
| `logout`    | セッションを破棄する                                                 |
| `holidays`  | 表示期間内の日本の祝日（ログイン不要）                               |
| `projects`  | プロジェクト一覧                                                     |
| `members`   | 対象プロジェクトの担当者候補（統合済み）                             |
| `statuses`  | 対象プロジェクトのステータス（名前で統合済み）                       |
| `issues`    | 課題取得。ページング・マージ・重複排除までサーバー側で完了させて返す |
| `icons`     | 担当者のアイコンを data URL でまとめて返す                           |
| `rateLimit` | レート制限の残量                                                     |

`holidays` 以外はすべてログインが必須です。誰の呼び出しかは Google のログインで決まるため、
セッション ID を発行してブラウザへ渡す必要はありません。

例外はクライアントへそのままの形で届かない（メッセージが加工され、状態コードが落ちる）ため、
成否は必ず `{ ok: true, data } | { ok: false, status, error, detail }` に包んで返します。

### 8.3 アイコンを URL ではなく data URL で返す理由

Backlog のアイコン取得はアクセストークンを要するため `<img src>` から直接は叩けません。
ウェブアプリには画像を返せる URL も無いので、サーバーで Base64 に変換して data URL として
渡します。行やグループ見出しに同時に数十個並ぶため、クライアント側で少し待ってから
まとめて 1 回で取りに行き、結果は `CacheService` に 6 時間置きます。

### 8.3 セキュリティ上の必須対策

1. **オープンプロキシ化の防止**: ログイン時のスペースは許可ドメインのみを受け付ける。
   `^[a-z0-9][a-z0-9-]*\.(backlog\.jp|backlog\.com|backlogtool\.com)$` にマッチしないリクエストは 400 で拒否する。この検証を怠ると、本アプリが任意ホストへの中継器になります。認可画面の URL もこの値から組み立てるため、検証は必須です。
2. **トークンをブラウザへ渡さない**: アクセストークンとリフレッシュトークンは利用者ごとの `PropertiesService` にのみ置き、ブラウザへは一切渡さない。
3. **CSRF 対策**: 認可リクエストの `state` にサーバーが払い出した使い捨ての値（nonce）を載せ、コールバックで照合して消費する。1 度使った nonce は削除して再利用を防ぐ。
4. **state に載せたスペースの再検証**: 認可 URL の組み立てはクライアント側で行うため、`state` に載るスペースはクライアント由来である。コールバックで受け取ったあと、必ず 1 の許可ドメイン検証を通し直す。
5. **キャッシュ分離**: キャッシュキーにはスペースとユーザー ID のハッシュ（SHA-256）を含め、別ユーザーのレスポンスが混ざらないようにする。アクセストークンは更新のたびに変わるためキーには使わない。
6. **ログに秘密情報を残さない**: エラーメッセージからアクセストークンをマスクする。
7. **エラーの転送**: Backlog からの 401 / 403 / 429 はステータスコードを保ったままクライアントへ返し、UI で適切なメッセージを出す。

## 10. 認証とデータの取り扱い

Backlog の OAuth 2.0（認可コードフロー）でログインします。

### フロー

```text
ブラウザ（iframe）        Apps Script（doGet）              Backlog
   │  画面を開く                │                               │
   │◀── HTML + nonce ───────────┤ nonce を払い出して保存        │
   │  スペースを入力            │                               │
   │  state = nonce|space|条件  │                               │
   ├── 最上位フレームを遷移 ────────────────────────────────────▶│
   │                            │            ユーザーが許可      │
   │◀──────────── 302 /exec?code=&state=（最上位フレーム）───────┤
   ├── GET /exec?code=&state= ─▶│                               │
   │                            │ nonce を照合して消費          │
   │                            │ state のスペースを再検証      │
   │                            ├── POST /api/v2/oauth2/token ─▶│
   │                            │◀── access / refresh token ────┤
   │                            ├── GET /api/v2/users/myself ──▶│
   │                            │ UserProperties に保存         │
   │◀── HTML（ログイン済み）────┤                               │
```

認可画面への遷移は、サンドボックス iframe の外（最上位フレーム）を動かすしかありません
（Backlog の画面は `X-Frame-Options` で iframe に表示できない）。最上位フレームの遷移は
ユーザー操作に由来していないと許されないため、`target="_top"` のリンクをクリックと同じ
同期処理の中で発火させます。そのぶん認可 URL の組み立てはクライアント側に置き、
`state` に載せたスペースをサーバーで検証し直す形にしています。

### 保存する場所

| 情報                                    | 保存先                                  | 備考                                                                      |
| --------------------------------------- | --------------------------------------- | ------------------------------------------------------------------------- |
| アクセストークン / リフレッシュトークン | `PropertiesService.getUserProperties()` | ブラウザには渡らない                                                      |
| セッションの有効期限                    | 同じレコードの `sessionExpiresAt`       | 30 日。保存し直すたびに延びる                                             |
| OAuth の nonce                          | 同じ領域（10 分、同時に 5 個まで）      | 照合して消費し、再利用を防ぐ                                              |
| 直前に入力したスペースドメイン          | ブラウザの localStorage                 | 秘密情報ではない                                                          |
| 直前の表示条件                          | ブラウザの IndexedDB                    | URL クエリと同じ文字列で 1 件。保存時のスペースが一致するときだけ復元する |

アクセストークンの寿命は 1 時間です。API 呼び出しの入口で残り 60 秒を切っていたら
リフレッシュトークンで更新し、更新後のトークンを書き戻します。Backlog は
リフレッシュトークンをローテーションするため、更新は `LockService` で直列化し、
ロックを取ってから保存済みの内容を読み直します。

### 既知のリスク

- `PropertiesService` の値は暗号化されません。スクリプトを編集できる人は、自分の領域の値を読めます。保持するのは有効期限付きのトークンだけに留めています。
- nonce を同時に覚えられるのは 5 個までです。6 つ以上のタブを開いてから最初のタブでログインすると失敗します（もう一度押せば通ります）。
- 表示できる範囲はログインしたユーザーが参加しているプロジェクトに限られます（Backlog 側の権限がそのまま効きます）。

## 11. パフォーマンス設計

| 施策                   | 内容                                                                                                                                                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| サーバー側キャッシュ   | `CacheService` の利用者ごとのキャッシュに 3 分（マスタ系は 30 分）。キーは `ハッシュ(スペース + ユーザー ID) + 正規化済みクエリ`。1 キーの上限（約 100KB）を超える応答は分割して保存する。「再読込」ボタンではキャッシュをバイパスする           |
| マスタのキャッシュ単位 | 担当者とステータスはプロジェクトごとに保存する。選択した組をキーにすると、選択を 1 つ変えるだけで選択数ぶんのリクエストが再び飛ぶ                                                                                                                |
| 並列取得の制御         | 課題ページングの並列度を 5 に固定。プロジェクト単位の統計取得も同様                                                                                                                                                                              |
| 行の描画コスト削減     | 各行に CSS の `content-visibility: auto` と `contain-intrinsic-size` を指定し、ビューポート外の行のレイアウト・描画をブラウザに省略させる。JavaScript による仮想スクロールを実装せずに済み、スクロール位置の管理やアンカーリンクの破綻も起きない |
| 横スクロールの同期     | 行ヘッダは `position: sticky` で固定し、タイムラインのみスクロールさせる                                                                                                                                                                         |
| 初回表示               | 期間の既定値を「今月の 1 日 〜 3 か月後の末日」とし、初回の取得件数を抑える。プロジェクトと担当者は未選択で始める（勝手に全選択すると、多数のプロジェクトに参加している人は開いた瞬間に重い取得が走る）                                          |
| 入力の待ち合わせ       | キーワードは入力が止まってから 800ms 後にだけ取得し直す。表示条件の IndexedDB への保存も 500ms まとめる                                                                                                                                          |

### スタイルの構成

スタイルは CSS Modules でコンポーネントごとに分割している。

| 置き場所                                | 役割                                                                       |
| --------------------------------------- | -------------------------------------------------------------------------- |
| `src/client/styles/global.css`          | デザイントークン（CSS カスタムプロパティ）とリセット。唯一のグローバル CSS |
| `src/client/styles/controls.module.css` | ボタン・入力欄など複数箇所で使う部品。各所から `composes` で取り込む       |
| `src/client/**/<Component>.module.css`  | そのコンポーネント専用のスタイル                                           |

状態（遅延・完了・バーの種類・切り詰めの有無）はクラス名ではなく `data-*` 属性で表し、
CSS からは `[data-overdue='true']` のように参照する。こうすることで、テストは `data-*`
だけを見ればよくなり、見た目の実装（クラス名の付け替え）から独立する。

SSR シェルは `<Script>` がビルド後の manifest を読み、対応する CSS の `<link>` も出力する。
そのため HTML 側で CSS ファイルを直接指定する必要はない。

### デプロイの前提条件

`main` への push で即デプロイするのではなく、**CI と CodeQL の両方が同じコミットで成功してから**
デプロイする（`workflow_run` による直列化）。

`workflow_run` はどちらか一方の完了ごとに発火するため、gate ジョブで次を確認する。

1. 起動元が push であること（CodeQL の定期実行でデプロイしない）
2. 起動元のワークフローが success であること
3. GitHub API で同じ SHA の CI と CodeQL の結論を引き、**両方 success** であること

先に終わったほうは相手が `pending` なので見送り、後に終わったほうがデプロイまで進む。
checkout する SHA は `workflow_run` のイベントから取るため、gate で 40 桁の 16 進で
あることを検証してから `ref` に渡している。

### 品質チェックの構成

| コマンド            | 内容                                    |
| ------------------- | --------------------------------------- |
| `pnpm format:check` | oxfmt による整形の確認                  |
| `pnpm lint`         | oxlint（type-aware ルール込み）         |
| `pnpm lint:css`     | stylelint による CSS の検査             |
| `pnpm lint:md`      | markdownlint による Markdown の検査     |
| `pnpm lint:actions` | actionlint による GitHub Actions の検査 |
| `pnpm spellcheck`   | cspell によるスペルチェック             |
| `pnpm typecheck`    | `tsc --noEmit` による型チェック         |
| `pnpm test`         | Vitest によるユニットテストと描画テスト |
| `pnpm verify`       | 上記をまとめて実行                      |
| `pnpm smoke`        | ビルド成果物が push できる形かの検査    |

テストは実装ファイルと同じディレクトリに `*.test.ts(x)` として置いています。対象は日付演算・ガント描画ロジック・URL 変換・スペース検証・認可 URL と state の組み立てと分解・OAuth（トークン交換 / 更新）・セッションと nonce の保存・キャッシュ（分割保存を含む）・Backlog クライアント（まとめ投げ・リトライ・トークンの masking）・課題取得のクエリ組み立て・API のガードとトークン自動更新・認可コールバック・各 React コンポーネントの操作・アプリ全体の統合テストです。Apps Script のサービスは `src/server/gas/` に閉じてあるため、テストではインメモリの実装を差し込むだけで済みます。Backlog の実データを叩くテストは含めていません。

`oxlint --type-aware` は型情報を使う lint ルールを実行するもので、型エラー自体は検出しません（実際に型エラーを仕込んで確認済み）。そのため型検査は `tsc --noEmit` で別途行っています。

整形は oxfmt に一本化しています。oxfmt は TypeScript / JavaScript のほか CSS・Markdown・JSON・YAML も扱うため、リポジトリ内の全ファイルが 1 つの整形ツールで揃います。lint はそれぞれ専用のものを使い、CSS は stylelint（CSS Modules の `composes` と lowerCamelCase のクラス名を許可）、Markdown は markdownlint-cli2（体裁は oxfmt に任せ、行長などのルールは無効）で検査します。

シェルスクリプトは意図的に置いていません。`.sh` が 1 つでもあると、そのためだけに shellcheck を足すことになりますが、npm の shellcheck はインストール時にバイナリを取得するもので、pnpm-lock.yaml による固定や `minimumReleaseAge` の保護から外れます。Claude Code のフックも `scripts/format-and-lint-hook.mjs` として Node で書き、リポジトリ内のすべてのファイルが oxfmt / oxlint の対象に入るようにしています。

oxlint のカテゴリは `correctness` / `suspicious` / `pedantic` をエラー、`perf` を警告として有効にしています。`style` と `restriction` は、`no-ternary`・`no-magic-numbers`・`oxc/no-async-await` のようにこのコードベースの書き方と衝突するルールが大半のため、カテゴリごとの有効化はせず、有用なものを個別に指定しています。`react-perf` プラグインは、ガントのバーが位置と幅を `style` 属性で受け取る都合上、`jsx-no-new-object-as-prop` が避けようのない検出を大量に出すため有効にしていません。

oxlint 本体に無い検査は、外部の ESLint プラグインを `jsPlugins` として読み込んで補っています。`jsPlugins` は oxlint 側で alpha 扱いかつ semver の対象外であり、すべてのバージョンを固定している本リポジトリの方針とは本来かみ合いませんが、本体では代えの利かない検査があるため例外として採用しています。

| プラグイン                    | 何を見るか                                                                                                                                  |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| eslint-plugin-css-modules     | `styles.xxx` が CSS 側に存在するか、CSS 側に使われていないクラスが無いか。CSS Modules はタイプミスしても `undefined` になるだけで気付けない |
| eslint-plugin-react-hooks     | React Compiler 由来のルール。`refs`（描画中の ref 参照）・`purity`・`immutability` など、oxlint 本体が持たないもの                          |
| eslint-plugin-regexp          | 正規表現の書き間違い。推奨セット 60 ルールをそのまま採用                                                                                    |
| eslint-plugin-no-unsanitized  | `innerHTML` などへの安全でない代入                                                                                                          |
| eslint-plugin-testing-library | Testing Library の使い方。`no-node-access` だけは、テスト環境で CSS Modules のクラス名が `undefined` になるため無効にしている               |
| eslint-plugin-sonarjs         | バグ・セキュリティ・正規表現の実行時間・テスト品質・認知的複雑度。279 ルールのうち本体と重複しないものだけを選択                            |

導入時に `sonarjs/super-linear-regex` が `normalizeSpace` のパス除去（`/\/.*$/`）を指摘しました。開始位置ごとに `.*` を試すため、スラッシュの多い入力で実行時間が入力長の二乗に近づくもので、この値はログイン画面から渡ってくるユーザー入力です。`indexOf` による切り出しに置き換えています。

lint の実行時間は 0.6 秒から 2.0 秒に増えました（`pnpm lint`、87 ファイル）。

## 14.5 日本の祝日

祝日は稼働日かどうかを判断する材料なので、土日と同じように背景を塗る。データは [holidays-jp](https://holidays-jp.github.io/) の `api/v1/date.json` から取る。Google カレンダーの祝日情報から自動生成されており、告示の変更に追従する。

取得できるのは**去年・今年・来年の 3 年分**で、それより先の期間は祝日を塗らない。数年先まで見渡すような使い方はしない前提で、祝日法の規則を自前で持たない判断にしている。規則計算は春分・秋分の近似式、振替休日、国民の休日、皇室行事やオリンピックに伴う一度きりの移動まで抱え込むことになり、正しさを保ち続ける手間に見合わない。

API が落ちていたり応答の形が違ったりした場合は祝日なしとして扱う。背景が出ないことは画面を止めるほどの問題ではないため、画面全体のエラーにはしない。

取得はサーバー側（`holidays`）で行う。ブラウザから直接叩かないのは、`CacheService` と実行内のメモ化で外部への往復を減らすためと、第三者サイトへの依存をサーバー側に閉じ込めるため。利用者に依存しない情報なのでスクリプト共通のキャッシュに置く。TTL は `CacheService` の上限に合わせて 6 時間。

内閣府も「国民の祝日について」のページで CSV を公開しているが、REST API ではなく Shift_JIS の CSV で、収録も 1955 年から翌年まで。カバー範囲は holidays-jp と変わらないため、扱いやすい後者を使っている。
